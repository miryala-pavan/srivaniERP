### 1.5 Debit Notes — itemized goods returns (the big one)

**Trigger**: user explained the real-world nuance — sometimes a supplier gives a formal credit note document, sometimes the return amount is just adjusted in a future bill, but **either way the actual returned items need to be tracked**, not just a rupee amount. Asked me to research how established ERPs (Tally, Zoho, Odoo, SAP) handle this before building.

**Research findings** (via WebSearch, cited to the user with sources):
- **Tally Prime**: purchase returns are recorded as a **Debit Note** (issued by the buyer), itemized, referencing the original invoice — NOT called "Credit Note" despite common usage of that term. A "Credit Note" in strict terms is what the *supplier* issues back.
- **Zoho Inventory/Books**: "Vendor Credit" — itemized lines, can reference the supplier's own credit note number, appliable to future bills.
- **Odoo**: cleanly splits stock reversal (a "Return" operation, itemized, reverses inventory) from the financial credit note (generated from the original bill, referencing the return).
- **SAP Business One**: document choice depends on whether the vendor invoice was already booked — "Goods Return" (inventory-only) before, "A/P Credit Memo" after.
- **Universal pattern found**: the return itself is always itemized by product + quantity, never a lump sum; money and goods are treated as related but separate concerns.

**Design decision made and implemented**: `PurchaseDebitNote` (already dormant in the schema) becomes the primary itemized-return document, used specifically for physical returns. `SupplierCreditNote` stays as-is, now scoped specifically to non-itemized supplier-initiated credits (scheme/rebate/rate-difference) with nothing physically returned. Both remain fully independent, both reduce the supplier's balance identically, both support optional linkage to the supplier's own paperwork via a `supplierCnNumber` field.

**Schema change**: added `supplierCnNumber String?` to `PurchaseDebitNote` (migrated locally, empty-diff confirmed). `PurchaseDebitNoteItem` already had every field needed (productId, productName, hsnCode, quantity, unitPrice, taxableAmount, gstRate, cgst/sgst/igst, cessAmount, totalAmount) — no changes needed there.

**Backend built** (`backend/src/grn/grn.service.ts`, `backend/src/grn/grn.controller.ts`):
- New `PDN` bill series (`PDN/2026-27/0001` numbering pattern, same as `SCN`) — added to the seed list in `backend/src/admin/admin.service.ts` (`seriesDefs` array) AND manually seeded into the local dev DB directly via script (a fresh business/new deployment would get it automatically from the admin seed; this dev DB needed the one-time manual insert since the seed endpoint wasn't re-run).
- `createPurchaseDebitNote(businessId, userId, userName, dto)` — itemized: takes an `items[]` array, computes taxable/GST/cess **per line**, sums to header totals, generates the PDN number, creates the note + nested items in one transaction. Status starts at `'ISSUED'` (the "counts toward balance" state).
- `cancelPurchaseDebitNote` — same void pattern as credit notes: sets `status: 'CANCELLED'`, permanent, no edit capability (matches "financial documents aren't mutated, only cancelled" convention already used for bills/credit notes in this codebase).
- `getPurchaseDebitNoteById` / `getPurchaseDebitNotes` (list) — mirror the credit note equivalents.
- Controller routes: `POST /grn/debit-notes`, `PATCH /grn/debit-notes/:id/cancel`, `GET /grn/debit-notes`, `GET /grn/debit-notes/:id`.

### 1.12 Batch 5 — SupplierCreditNote GL journal, POS void/return GL reversal, and a serious pre-existing bug found along the way (session 2, same day)

1. **`SupplierCreditNote` now posts a real GL journal.** It already reversed ITC (batch 3) but had no `JournalBridgeService` entry at all. Added `postCreditNoteJournal()` — unlike a Debit Note (physical goods return, offsets Stock), a scheme/rebate credit note has no stock movement, so it offsets the new `ACC.PURCHASE_RETURNS` account (`5002`, already in the seeded CoA, just not previously mapped) instead: `Debit Payables / Credit Purchase Returns + ITC reversal`, with the mirrored reversal on cancellation. **Verified live**: a real ₹118 test credit note posted a balanced journal (Payables 118 = Purchase Returns 100 + CGST 9 + SGST 9); cancelling it posted the exact reversal.

Extended `postSaleJournal()` with an `isCancellation` flag that swaps every line's debit/credit (always exactly balanced, since swapping a balanced set stays balanced) rather than writing a separate reversal builder. Added the shift-total decrement to `voidBill()`'s existing transaction, mirroring `createBill()`'s own increment logic. **Verified live**: a real ₹180 cash bill correctly showed in shift totals (180/1/180), then voiding it correctly reversed the GL journal (Cash credited 180, Sales+CGST+SGST debited 152.54+13.73+13.73) and reset shift totals back to exactly 0/0/0.
3. **POS sale-return (`createCreditNote`, the customer-facing refund credit note) also had zero GL footprint — fixed.** Added `postSaleReturnJournal()`: `Debit Sales + CGST/SGST/IGST reversed`, `Credit Cash` (refundMode `CASH`) or `Credit Bank` (`BANK_TRANSFER`) or `Credit Receivables` (`STORE_CREDIT` — same account `postSaleJournal` debits for a credit sale, just the other direction, since a store-credit refund is functionally "we now owe the customer / they owe us less"). **Verified live** (via direct `postSaleReturnJournal` calls, since a real end-to-end test kept colliding with a separate pre-existing bug — see below): both `CASH` and `STORE_CREDIT` modes produced correctly balanced journals crediting the right account (`1001` vs `1100`).
4. **Found and fixed a serious, confirmed, pre-existing bug while verifying #2 above: `SalesItem` has never had a `pluId` column, so `voidBill()`/`createCreditNote()`'s stock-restoration logic — which both read `item.pluId` to restore the *exact* original PLU — has always silently no-op'd.** `(item as any).pluId` was reading a property that doesn't exist on the model at all (not just unset — the schema had no such column, and it was never referenced anywhere else in the codebase either). Every void and every sale-return in this app's history wrote a *compensating* `StockLedger` row (making the ledger *look* internally consistent) while the actual `ProductPlu.stockOnHand` / `Product.totalStock` — the counters the rest of the app reads for real availability — silently stayed wrong, permanently understated by the voided/returned quantity. 5. **Side-discovery, not fixed**: `CreditNote.creditNoteNumber` is a bare global-`@unique` field, not scoped per business — confirmed by directly colliding with it while building the verification for #4 (a fresh throwaway test business's first CN number collided with Srivani Stores' already-used number). Not a live problem today (single-tenant), but a real landmine for actual multi-tenant use.
